## Session: implement issue #36 — webhooks for flag change events

- Applied `conventions/stale-issue-scope-verify-before-implementing` first: grepped the codebase and
  found the `@Async @TransactionalEventListener(AFTER_COMMIT)` pipeline, `@EnableAsync`, a `RestClient`
  bean and 3 events already in place from the Slack work — so webhooks became a **second consumer** of
  a proven pipeline rather than new infrastructure.
- **Found a contradiction in the acceptance criteria** and raised it before coding: the AC wants
  signatures verifiable with the shared secret *and* the secret "hashed/encrypted". Hashing is
  impossible with HMAC (needs plaintext per delivery), and the repo's `ApiKeyHasher` precedent points
  the wrong way. Human confirmed **AES-GCM encryption** + a new `APP_WEBHOOK_ENCRYPTION_KEY`, and
  **fan-out to every environment in the project** for project-scoped events.
- Built: migration 012 (3 changesets), `SecretCipher` (AES-256-GCM), `SsrfGuard`, `WebhookSigner`,
  `WebhookSender` (3 attempts, doubling backoff, every attempt persisted), `WebhookDispatcher`, full
  CRUD at `/api/v1/webhooks` with one-time secret reveal, `WebhookProperties` with JwtProperties-style
  fail-fast validation. Enriched 3 existing event records with ids + added 2 new events.
- Integration test uses a real JDK `HttpServer` on loopback and a `TransactionTemplate` publish (must
  NOT be `@Transactional` or AFTER_COMMIT never fires) — asserts a real signed POST, verifies the
  signature with the secret, and asserts 3 recorded attempts against a 500-ing endpoint.

## Session (cont.): implement issue #37 — flag hygiene

- Verified scope against the code first: found `EnvironmentRepository.touchLastUsedAt` +
  `ApiKeyAuthenticationFilter` as an exact precedent for throttled write-on-read, so #37 mirrors it
  rather than inventing a pattern.
- **Caught a would-be production-only bug while writing it:** the SDK evaluation path is
  `@Transactional(readOnly = true)`, so the usage UPDATE joins a read-only transaction — PostgreSQL
  rejects that, H2 allows it. Default propagation would have passed CI and failed in prod. Fixed with
  `REQUIRES_NEW` and pinned by an integration test that asserts real persistence.
- Also deliberate: the touch stays a bulk JPQL UPDATE so `@UpdateTimestamp` does not fire (an entity
  setter would bump `updated_at` on every read); the tracker is called outside any cache-load function
  so a #30 cache hit cannot make hot flags look stale.
- Report is per (flag, environment) pair — staleness is per-environment, and each row's `enabled`
  surfaces the real risk case: an expired flag still on in production. Expiry reports, never disables.
- `./mvnw clean verify`: 271 tests, 0 failures (+28), Spotless clean, coverage met. → `decisions/0023`.
