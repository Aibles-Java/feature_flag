- [Deploy failure-logs: `docker logs ff_app`, not `docker compose logs`](decisions/0031-deploy-logs-avoid-compose-interpolation.md) — a `deploy` run showed only `error while interpolating … APP_JWT_SECRET/APP_IMAGE/POSTGRES_* missing` + exit 1, looking like a missing-secret failure — but `ff_app` was healthy on the prior image and secrets were fine. Tell: **`APP_IMAGE` (not a secret, set from `steps.img` in the Deploy step's `env:`) also reported missing** ⇒ the failing command ran in an **env-less step**. Cause = 3 facts compounding ([[0022-cd-deploy-prod-self-hosted-compose]]): `docker compose` re-interpolates the **whole** file for *any* subcommand incl. `logs`; every var is `${VAR:?}`-guarded (empty ⇒ hard error, by design); GHA **step env is isolated**. The failure-path `docker compose … logs app` in *Verify deployment health* + rollback carried no `env:`, so it blew up on `:?` and **masked the real app logs**. Fix: `docker logs --tail=100 ff_app || true` (addresses container by fixed name, **never parses compose**, needs no vars) at lines ~391/~432; left Deploy/rollback `compose up/pull/ps` untouched. The scary log "about the variables" ≠ bad secrets — it's the step not passing them. **Pattern:** only use `docker compose <cmd>` in a step supplying every `${VAR:?}` it needs; for a failure-path log dump prefer `docker logs <fixed-name>`.
